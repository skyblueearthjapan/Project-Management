## 1. はじめに

### 1.1 プロダクトの目的

産業用機械メーカーの社内設計者・購買・製造担当者向けの **出図管理 + 軸別進捗管理 + メール送信ハブ** アプリケーション。

設計者が出図した PDF / DXF を、工番（こうばん、案件番号）と軸（昇降軸／旋回軸／回転軸 等）の二軸で整理し、出図から組立出図・出荷までの **10工程の進捗** を全員で共有できる状態を目指す。

加えて、出図通知だけでなく **差替図面メール・購入部品の納期回答のやり取り** など、設計現場の社外/社内メール送信窓口としても機能する。

### 1.2 既存資産との関係

- **Stock Management** (`C:\Users\imaizumi.LINEWORKS-NET\Documents\Stock Management`) — 部品ライブラリアプリ。**同じ社内Excel（新一覧 / 日程表A）を参照する** が、DB・サービスは **完全独立**
- **Marin-PDF-Workspace** (`C:\Users\imaizumi.LINEWORKS-NET\Documents\Marin-PDF-Workspace`) — PDFビューア参考。**PDF描画の大きさ・操作感** を踏襲（ただし機能は閲覧+印刷のみ）

### 1.3 デザイン方針 ⭐ v1.0.4 更新

**Linear / Notion 風のミニマルデザイン**。Anthropic Design バンドルの「Project Management」を準拠とする。

- **白基調** (`#ffffff`) + **極薄 hairline** (`#eceef2`) で罫線を引く
- **Cyan単色アクセント** `#06b6d4` (進行中・主要アクション・選択状態のみに使用)
- **テキスト5段階階層**: `ink #0c1626 / ink2 #5a6473 / ink3 #9aa3b2 / ink4 #c4cad3`
- **フォント**: 本文 Inter Tight + Noto Sans JP、工番/パス/% は JetBrains Mono
- **角丸**: 6-10px (シャープに)
- **装飾を極力削ぐ** — グロー・シマー・大きなシャドウは廃止

詳細は [WIREFRAMES.md](./WIREFRAMES.md) §9 デザイントークン参照。

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| 工番 (job_no) | 個別案件番号。例: `25214`、`TS25214`（プレフィクス変種あり） |
| 元工番 (parent_job_no) | 親案件番号。Stock Management でも採用済みの設計者主要キー |
| 軸 (axis) | 1工番内の機構分割単位。例: 全体図 / レイアウト / 昇降軸 / 旋回軸 / 回転軸 / 前後軸 / 走行軸 など。**完全自由命名**、工番ごとに追加可 |
| 出図 (release) | PDFをこのアプリに登録し、他メンバーに公開する行為。**軸単位**で行う |
| 出図履歴 (release log) | 軸ごとの出図イベントを timestamp 付きで全件保持。差替出図でも上書きせず追記 |
| 工程 (step) | 10ステップの進捗段階。出図前チェック → 設計出図 → ... → 組立出図 |
| 進捗 (progress) | 軸ごとの工程ステータス。各ステップ「未着手 / 進行中 / 完了」を持つ |
| 連絡先 (contact) | メール送信の宛先マスタ。出図通知・差替連絡・納期回答 等で都度選択 |
| テンプレート (template) | メール用途別の件名・本文ひな型。用途タグ付きで複数保持 |
| DXF | AutoDesk Drawing eXchange Format。製作部品の CAD図面ファイル |
| **関連資料 (related document)** | 工番に紐付くパス参照型ドキュメント (Excel部品リスト・材料取り資料・加工指示書PDF等)。**1つの資料に複数バージョンを持てる** |
| **資料グループ (group code)** | 関連資料の種別。`parts_list` (部品リスト) / `material` (材料取り) / `instruction` (加工指示書) / `other` |
| **部品手配 (parts order)** | 関連資料 (主に部品リスト) を業者・社内に送信し、返却 (手配済み) を待つワークフロー。`未送信 / 送信済 / 返却済` の3状態 |
| **差し替え図面 (PDF replacement)** | 軸PDFを新版に差し替えた履歴。差し替え前後のパス・理由・送信メールを紐付けて時系列保持 |

## 3. 対象ユーザーと利用環境

### 3.1 ユーザー
- 同時利用者数: **4〜10名**
- 主な利用者: 機械設計担当者、購買担当者、製造担当者、品質チェック担当者
- 階層: **管理者 / 一般 の区別なし**（認証なしのため）

### 3.2 利用環境
- アクセス範囲: **社内LANのみ**（社外からのアクセスは Firewall + IP制限で**遮断**）
- クライアント:
  - **PC**: Chrome / Edge + 出図担当者のローカル Outlook (主要利用端末)
  - **タブレット**: iPad / Android タブレット (社内Wi-Fi接続、閲覧専用)
  - **スマホ**: iPhone / Android (社内Wi-Fi接続、閲覧専用)
- 認証: **なし**
- 接続: 社内Wi-Fi に接続している間のみアクセス可能（社外不可）

### 3.3 セキュリティポリシー（社内LAN限定）

社内LANのみ・社外不可を **多層** で実現:

| 層 | 対策 |
|---|---|
| Docker | `ports` をサーバーLAN IP に **バインド固定**（`0.0.0.0` 公開禁止） |
| Windows Firewall | LANサブネット（例: 192.168.X.0/24）のみ inbound 許可、それ以外 deny |
| Nginx | `location /` に `allow 192.168.X.0/24; deny all;` を二重で記述 |
| TLS | 自己署名 or 社内CA HTTPS（mitm対策） |
| SMB | マウントは **`:ro`（read-only）**、削除系関数（`os.remove` / `Path.unlink` 等）を pre-commit で禁止 |
| CORS | 同一オリジン前提、外部オリジン拒否 |
| 監査 | 出図履歴・進捗更新・メール送信ログを全件 timestamp 付保存 |

## 4. 機能要件

### 4.1 工番マスタ連携 ★ Stock Management と同じ Excel ソースを参照

製品名・お客様名・納期は本アプリに保持せず、**元工番をキーに外部 Excel から派生取得**。

#### マスタファイル（v0.1 確定）
| ファイル | パス | 取込シート | 役割 |
|---|---|---|---|
| 新一覧.xlsm | `\\lineworks-sv\Data\総務部\社内\日程表\新一覧.xlsm` | 「正」（約8,166行） | 全工番履歴 |
| 日程表A.xlsx | `\\lineworks-sv\Data\総務部\社内\日程表\日程表A.xlsx` | A / TS / EM / コマツ金沢 の4シート集約 | アクティブ工番 + 納期 |

#### アクセス手段
- **SMBマウント経由**（`:ro`）。Google Sheets API / 社内DB は不要
- ファイルへの書き込み・削除は **コード上で一切禁止**

#### 取得項目
- 元工番 (`parent_job_no`)、受注先 (`extra.dealer`)、納入先 (`customer_name`)、品名 (`product_name`)、契約納期 (`due_date`)、担当 (`owner`)、その他は `extra.*` JSONB

#### 同期方式
- **APScheduler によるポーリング監視**、60秒間隔（mtime ベース）
- 2フェーズ同期（Phase1: 新一覧で全件UPSERT → Phase2: 日程表Aで `is_active=true` を反転）
- ロックファイル (`~$xxx.xlsx`) 検出時はスキップ
- 失敗時は既存キャッシュ維持、5回連続失敗で管理画面に警告

#### 手動同期
- 管理画面と ⌘K に「今すぐ同期」ボタン

#### Stock Management との独立性
- **DB完全独立**。Stock 側の `job_master_cache` テーブルは参照しない
- 同じ Excel ソースを別 mtime / 別 DB に保存（**重複読込あり、許容**）

### 4.2 工番登録と軸管理

#### 4.2.1 工番登録フロー
1. ユーザーが新規登録ボタンを押す（または ⌘K → 「工番を登録」）
2. **工番選択ピッカー** が開く
3. 検索窓に文字入力 → `job_master_cache` から候補絞り込み（例: `2500` → `25001`〜`25099` の候補表示）
4. 候補リストに **工番 + 納入先 + 製品名 + 納期** を一覧表示
5. クリック → 工番を選択
6. 工番一覧（ホーム画面）に登録される。この時点では軸ゼロ・進捗ゼロ

#### 4.2.2 軸の追加
- 工番詳細画面の **軸タブバー** に `+ 追加` ボタン
- クリックで小モーダル → **軸名を自由入力**（例: `全体図`、`昇降軸`、`旋回軸`、`走行軸`）
- 既存軸名サジェスト（過去工番で使われた軸名候補）も表示
- 同一工番内で **軸名の重複は禁止**
- 軸の削除はインライン操作、Undo Toast あり

#### 4.2.3 軸ごとの保持データ
- 軸名 (`name`)
- 表示順 (`display_order`)
- PDFパス参照（1軸=1ファイル、複数ページ可）
- DXFフォルダパス参照（1軸=1フォルダ）
- 進捗ステータス（10工程ぶん）
- 出図履歴（複数回ぶん全件）

### 4.3 出図フロー

#### 4.3.1 出図のタイミング
- **アプリの軸に PDF パスを登録した瞬間** = 出図とみなす
- 軸ごとに独立して出図できる（全体図だけ先に出図、後で昇降軸を出図 等）
- 同じ軸を **後日 別 PDF で差替出図** することも可能（出図履歴に追記）

#### 4.3.2 PDFパス登録方法
**Stock Management の A+Bハイブリッド** を踏襲:

| 案 | 方式 |
|---|---|
| A | サーバー上のディレクトリツリーをUI表示、クリックで選択（ファイルブラウザ） |
| B | ブラウザに PDF を D&D → サーバーで SHA-256 計算 → 同ハッシュの既存ファイルを検索 → ヒットしたパスを紐付け |

**実体アップロードは行わない**（パス参照のみ）。

#### 4.3.3 出図通知
- 出図ボタン押下時、**通知作成モーダル** が開く
- モーダル内:
  - 件名・本文（用途別テンプレートから自動補完）
  - 宛先（連絡先マスタからチェックボックスで選択）
  - 添付（出図対象のPDFパスを参考表示、Outlook側で添付するかは送信者判断）
- 確認後、「Outlook下書きを作成」ボタンで送信
- 詳細は **§4.7 メール送信機能** 参照

#### 4.3.4 出図履歴
- 軸ごとに `release_logs` テーブルへ追記
- フィールド: 軸ID、PDFパス、出図者名、出図日時、出図通知メール下書きID（任意）、コメント
- 上書きはせず、**全件残す**
- 出図履歴は詳細画面の「履歴」タブで時系列表示

### 4.4 進捗管理（10工程・軸別）

#### 4.4.1 工程定義 ⭐ v1.0.4 short_label 追加
固定の10ステップ、`progress_steps` テーブルで管理（将来拡張可）。**short_label は詳細画面の進捗サブヘッダーや一覧画面の小さな表示で利用**:

| # | コード | 表示名 (`label`) | 短縮 (`short_label`) | 補足 |
|---|---|---|---|---|
| 1 | `pre_check` | 出図前チェック | 前検 | **第三者チェック**、担当者名を必須記入 |
| 2 | `design_release` | 設計出図 | 設計 | このアプリに登録し他メンバーに公開した状態 |
| 3 | `stock_check` | 在庫チェック | 在庫 | 部品が在庫にあるかStock Management等で確認 |
| 4 | `purchase` | 購入 | 購入 | 購入部品を発注 |
| 5 | `material` | 材料 | 材料 | 製作部品の材料を準備 |
| 6 | `material_check` | 材料チェック | M検 | 材料の質・量チェック |
| 7 | `factory_release` | 工場出図 | 工場 | 工場に図面を渡し製造開始 |
| 8 | `mizusumashi` | 水すまし | 水す | 部品を回収・搬送する工程 |
| 9 | `bolt` | ボルト | ボル | ボルト類の準備・取付 |
| 10 | `assembly_release` | 組立出図 | 組立 | 組立工程に図面を渡す |

> 出図前チェックは「第三者チェック」のため担当者名フィールドを **必須**。他の工程は担当者名は任意（記入できるがブランクOK）。

#### 4.4.2 進捗状態
各工程は3状態:
- `pending` (未着手)
- `in_progress` (進行中)
- `done` (完了)

#### 4.4.3 進捗操作
- 認証なし、**誰でもクリックで進められる**
- 工程アイコンクリック → 状態がトグル（pending → in_progress → done → pending）
- 担当者名フィールド: 出図前チェックのみ必須、他は任意
- 完了時刻は自動記録、誰がやったかは担当者名フィールドから（記入されていれば）
- 取り消し: Undo Toast（5秒以内）

#### 4.4.4 一覧での可視化 ⭐ v1.0.4 更新
- 一覧では**工番1行に集約進捗バー1本** (高さ 4px の細線)
- 構成 (行レイアウト): `★ | 工番(mono) | 顧客 | 製品 | N軸 | 納期 | %`
- バー: `cyan fill (width=pct%)` + 10個の **white tick** (1/10 区切り) + **円ドット** (現在位置 = nowPhase)
- バー下部: 10工程の **短縮ラベル** (前検/設計/在庫/購入/材料/M検/工場/水す/ボル/組立)
- フィルタタブ: すべて / 進行中 / 期限超過 / 今週 / スター
- 並び順: 納期 / 進捗 / 工番
- 詳細はワイヤーフレーム参照

#### 4.4.5 進捗サブヘッダー (詳細画面) ⭐ v1.0.4 新規
- 詳細画面の **軸タブ直下** に独立行として配置 (`progress-sub`)
- 構成: `軸名 | "⑦工場出図 進行中" 風のステータステキスト | 4px進捗バー + 短縮ラベル | パーセント | [軸を出図] ボタン`
- 役割: 現在見ている軸の状態を一目で把握 + ワンクリックで出図モーダル起動
- レスポンシブ (モバイル): 2行折り返し、`[軸を出図]` は非表示 (PC のみ、モバイルはヘッダーの [出図] で代替)
- **DXFペインからは進捗・出図ボタンは削除** (DXFは DXFファイルだけ表示する責務に専念)

### 4.5 PDF閲覧（Marin風、機能は閲覧+印刷のみ）

#### 4.5.1 描画
- `pdfjs-dist` でブラウザ内描画
- 1軸=1PDF、複数ページの場合は縦スクロールで全ページ表示
- 描画品質: Marin と同じく **大きく見やすく**

#### 4.5.2 操作
- ズーム: ボタン or `Ctrl+Wheel`（30〜300%、10%刻み）
- ページ送り: `PageUp/PageDown`、サムネペイン、ナビゲーションレール
- **FIT機能**: 現在ページの高さを viewer 高さに合わせる（Marin と同じ）
- ページ位置保持: ズーム変更後も現在ページを `scrollTo()` で復元
- 印刷: ブラウザ標準印刷ダイアログを起動
- **差替・結合・分割は実装しない**（Marin のうち view + print 相当のみ）

#### 4.5.3 PDF差替のフロー（出図差替えとは別）
- 出図差替えは **§4.3 出図フロー** を再度走らせる（新しい PDF パスで登録）
- 履歴は `release_logs` に追記、表示は最新版

### 4.6 DXFフォルダ表示と DXF Viewer

#### 4.6.1 DXFフォルダパス紐付け
- 軸ごとに **DXF フォルダ** を1個紐付け
- 登録方法は §4.3.2 と同じく A+B ハイブリッド（ただし対象はフォルダ）
- フォルダ内の `.dxf` ファイルを全件スキャン

#### 4.6.2 DXFリスト表示 (右ペイン専用) ⭐ v1.0.4 更新
- 詳細画面の **右ペインは DXFリスト専用** にシンプル化
- 進捗バー・出図ボタン・関連資料・差し替え図面 は右ペインから **すべて削除** (それぞれ §4.4.5 / §4.7 / §4.9 で別の場所に配置)
- 構成: `[ペインヘッダー: DXF + count + 全画面アイコン]` + `[DXFファイル一覧]`
- 1行 = 1 DXF ファイル (アイコン + ファイル名 + 表示名 + 日付)
- 表示項目: ファイル名 / 表示名（DXF 内の TITLE か無ければファイル名から拡張子を除いたもの）/ 更新日時
- ファイル数が多くても見やすい（スクロール、固定行高）
- **折りたたみトグル** (chevron) で右ペイン全体を開閉可能。PC は横方向、モバイルは縦方向

#### 4.6.3 DXF Viewer
- DXF行クリック → **DXF Viewer モーダル or 別画面** が開く
- 描画:
  - エンティティ: LINE / CIRCLE / ARC / POLYLINE / LWPOLYLINE / SPLINE / TEXT / DIMENSION 等の基本対応
  - レイヤー切替は v1 不要（v2 で追加可）
  - 色は DXF 内の定義に従う
- 寸法計測:
  - **2点クリックで距離測定**（mm 単位、DXF $INSUNITS から推定）
  - **3点クリックで角度測定**
  - 測定結果は画面上にオーバーレイ表示、クリア可能
- 操作:
  - ズーム: マウスホイール
  - パン: 左ドラッグ
  - リセット: ボタン

#### 4.6.4 ライブラリ候補（実装時に最終決定）
| 候補 | 評価 | コメント |
|---|---|---|
| **dxf-viewer** (vagran/dxf-viewer) | ◎ | three.js ベース、エンティティ対応広い、MIT、寸法計測は自作する必要あり |
| **three-dxf** (gdsestimating/three-dxf) | ◯ | three.js ベース、軽量、依存少、エンティティ対応は限定的 |
| **dxf-parser + 自作レンダラー** | △ | パース安定、ただしレンダラー全部自作になる |

> v1 では **dxf-viewer** を本命候補とし、寸法計測機能（距離・角度）は three.js の Raycaster + DOM オーバーレイで自作実装。
> 実装フェーズで実 DXF サンプルで動作検証し、最終確定。

### 4.9 差し替え図面と履歴 ⭐ v0.2 新規

#### 4.9.1 概要
軸PDFを新版に差し替えた際、**一括PDFのパス参照は1本のまま** で、別途 **差し替え履歴** を時系列で保持する。
旧PDFファイル自体は当面 UI では表示しない (実体はサーバー上に残る可能性あり、運用任せ)。

#### 4.9.2 差し替えのトリガー
| シナリオ | 動作 |
|---|---|
| **既存軸のPDFを更新** | 軸詳細画面で `[PDF を差し替え]` → 新パスを選択 → 理由コメント入力 → 確定で旧パスを履歴に保存し、軸の `pdf_path` を新パスに更新 |
| **差し替えメールを送信** | 差し替え連絡メール (テンプレ `redraw`) を送ると、メール送信ログと差し替え履歴が紐付く |

#### 4.9.3 差し替え履歴の保持項目
| 項目 | 内容 |
|---|---|
| 軸ID | どの軸の差し替えか |
| 旧PDFパス | 差し替え前のパス (履歴情報、UIには現状表示しない) |
| 新PDFパス | 差し替え後の新パス |
| 理由 | 差し替えコメント (例: 「ボルト位置を修正」) |
| 差し替え者 | 操作者名 |
| 差し替え日時 | timestamp |
| メールログID | 差し替え連絡メールへのリンク (任意) |

#### 4.9.4 UI ⭐ v1.0.4 大幅変更
**従来の「差し替え図面タブ」は廃止**し、以下に変更:

- 詳細画面の **軸タブ右端のアクションボタン** `[差し替え図面]` を配置
- クリックで **PDF差し替えモーダル** (`PdfReplaceModal`) が直接開く:
  - 新PDFのアップロードゾーン (PCからアップロード方式)
  - 差し替え理由テキストエリア (必須)
  - `[差し替え連絡メールを作成する]` チェックボックス (デフォルトON)
  - フッター: `[キャンセル]` `[差し替え + メール →]`

  - `axes.pdf_path` を新パスに更新
  - `pdf_replacements` に旧パス・新パス・理由・差し替え者・日時を INSERT
  - メール作成チェック時、MailComposeModal に遷移
- **差し替え履歴の閲覧**は **出図履歴モーダル** に統合 (§4.3.4 出図履歴 = 出図 + 差し替えイベントの統合タイムライン)

#### 4.10.6 Outlook 連携（ハイブリッド方式）
ブラウザがクライアントPCの Outlook を起動する2方式を併用:

```
[Outlook下書き作成ボタン押下]
    ↓
[ブラウザ → http://localhost:NNNN/health へ HEAD]
    ↓
  ┌──────────────────────────────────────────┐
  │ 200 OK = 常駐exeあり                       │
  │  → POST /draft で Outlook COM 経由        │
  │    下書き直接作成                          │
  ├──────────────────────────────────────────┤
  │ Timeout / 404 = 常駐exeなし                │
  │  → サーバーが .eml ファイルを返す          │
  │    ブラウザがダウンロード                  │
  │    ユーザーがダブルクリック                 │
  │    → Outlook 新規メール窓が開く            │
  └──────────────────────────────────────────┘
```

- **デフォルトは EML 方式**（インストール不要）
- 各PCに **常駐exe（任意配布）** があれば、より高速かつ下書きフォルダに直接保存
- 常駐exeは別配布、本アプリ本体は EML だけで完結する

#### 4.10.7 メール送信ログ

## 7. 制約・前提

- ファイル実体は社内 Windows ファイルサーバー集約
- アプリは **パス参照のみ**、実体はアップロードしない (PDF差し替え時のみ例外的にアップロード→所定フォルダに保存)
- 同じ Excel ソースを Stock Management と二重読込する（許容、Stock とは DB 独立）
- ファイル移動・削除によるリンク切れは定期検証バッチで検出
- 認証なしのため、悪意ある内部利用者対策は **社内LAN限定 + 物理アクセス管理** で吸収
- **モバイル/タブレット対応済** (v0.3): 社内Wi-Fi接続スマホ・タブレットから閲覧 + DXF寸法計測可
- バーコード / QR は将来検討

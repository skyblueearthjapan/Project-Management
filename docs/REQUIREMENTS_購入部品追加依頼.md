## 0. 設計の大原則(ユーザーと合意済 / 2026-07-27)

> **DOVE は「記録する場所」であって、「見せる場所」とイコールではない。**

- **記録は欠かさず全部入れる** — 工番未定の依頼も、枝番も、購入依頼だけで発生した工番も、すべて DB に残す。
- **UI に出すかどうかは別の判断で、後からいくらでも変えられる** — 紛らわしいものは出さない。必要になったら出す。

この非対称性が本アプリの設計方針の土台である。**DB に入れなかったものは後から復元できないが、
DB にあるものを表示しないのはいつでも取り消せる。** よって「記録は最大限・表示は最小限」から始める。

この原則により、「購入依頼だけの工番が DOVE の工番一覧を汚す」等の懸念は
**設計上のリスクではなく表示上の設定** に格下げされる。

## 1. 目的・背景

- 設計部員が「出図済みの機械に、後から購入部品を追加で手配したい」ときの依頼を、
  Outlook 手打ち + Excel 手動添付から **EXE のボタン一つ** に置き換える。
- 資材購買担当(五十嵐様)の手配結果を、**紙資料の手渡し配布からデジタル化**する。
- 依頼〜手配〜回答の**往復とステータスを一元管理**し、「何が依頼されていて、何が未対応か」を可視化する。
- 依頼履歴を **DOVE の工番に紐づけて**参照できるようにする。

### 現状の業務フロー(置き換え対象)

```
設計部員 --(Outlookを起動し部品リストExcelを手動添付)--> 五十嵐様
五十嵐様 --(商社へ手配 → 納期回答を紙に印刷)--> 各設計部員へ手渡しで配布
```

### 置き換え後

```
設計部員 [EXE] --(自動でメール + DOVE登録)--> 五十嵐様
五十嵐様 [EXE] --(未対応一覧から選択 → スキャンPDF添付 → 返信 + ステータス更新)--> 依頼元の設計部員
                                    ↓
                            DOVE(唯一の記録)
```

## 3. 現状データの実測(2026-07-27 時点 / 設計判断の根拠)

| 項目 | 実測値 |
|---|---|
| DOVE `jobs`(登録済み工番) | **22件**(全件が出図済み = 軸が1件以上ある) |
| 日程表マスタ `job_master_cache`(アクティブ) | **100件以上**(API上限で頭打ち) |
| うち DOVE 未登録 | **100件以上** |

→ **「購入依頼したい工番が DOVE に無い」は例外ではなく通常ケース。**
「DOVE にある工番だけ依頼できる」仕様は成立しない(§4.3 で対応)。

### 工番 ID 体系のズレ(実装上の最重要注意点)

| | 表記例 |
|---|---|
| 日程表マスタ(`job_master_cache`) | `25146-1` / `25146-2` — **枝番あり・LW接頭辞なし** |
| DOVE の工番(`jobs`) | `LW25146` — **親工番・LW接頭辞あり** |

**この2つは直接照合できない。** DOVE 側で `LW25146` をマスタから引いても空振りする。
既存の出図EXEは以下の二段構えで回避しており、本アプリも**同じ方式を踏襲する**:

1. Job を作る ID は **親工番**(`LW25146`) — `kouban.to_job_id()`
2. 納入先・製品名の照合は **枝番キー**(`25146-1`)でファイルサーバの Excel を直接読む — `master.py`
3. 引けた情報を登録リクエストに載せて DOVE へ渡す(DOVE 側の master 直引きには依存しない)

## 4. 用語・データモデル対応

| 業務用語 | 保持先 | 単位 |
|---|---|---|
| 親工番(例 `LW25146`) | **Job**(既存 `jobs`) | 1工番 = 1 Job |
| 枝番(例 `25146-1`) | 依頼レコードの**文字列項目** | 依頼ごと |
| 購入部品追加依頼 | **新テーブル `purchase_requests`** | 1依頼 = 1レコード |
| 部品リスト Excel | 依頼レコードに**アップロードして保管**(各自のPC上にあるため) | 1依頼 = 1ファイル |
| 手配結果の紙資料(スキャンPDF) | **新テーブル `purchase_request_replies`**(アップロード) | 1依頼 = 0〜n件 |
| 宛先・CC・役割 | ファイルサーバ上の**マスタExcel 1つ** | 全社共通 |

### 4.1 枝番の扱い(決定 / ①)

- 工番の紐づけは **親工番**。枝番は依頼レコードに**文字列項目として付帯保持**するのみ。
- **枝番を構造(階層・親子関係)としてモデル化しない。** 枝番は本来存在しないはずの例外であり、
  構造として作り込むと運用が正常化したときに不要な複雑さだけが残るため。
  文字列1項目なら、あってもなくても破綻しない。
- EXE では枝番を常に表示する(五十嵐様がどの案件か判別できるようにするため)。
  DOVE UI での表示可否は §5.3 の方針に従う。

### 4.2 工番未定の扱い(決定 / ②)

- `purchase_requests.job_id` は **NULL 許容**。工番が決まる前の先行手配依頼を受け付ける。
- 工番が決まったら**後から紐づけ直せる**。**設計部員・五十嵐様の両方が実行可能**(決定)。
- 工番未定の依頼は **EXE には表示するが、DOVE UI には出さない**(§5.3)。

### 4.3 DOVE に無い工番の扱い(決定 / ③)

- EXE の工番選択は **DOVE の `GET /jobs/master/search`** を使う
  → 日程表にある工番はすべて候補に出る(DOVE 未登録でも選べる)。
- 依頼登録時に **Job を get-or-create** する(出図EXEの `_get_or_create_job` と同一パターン。実績22件)。
  - 既存 Job があれば再利用。アーカイブ済みなら自動復活(既存挙動と同じ)。
  - 無ければ、EXE が枝番照合で取得した品名・客先・納期を使って新規作成。
- 新規作成された Job には **発生元(`origin`)= `purchase`** を記録する。

## 5. 機能要件

### 5.1 EXE(配布形態: **1本**・決定)

**役割は Windows アカウントで自動判定する。** マスタExcel の役割列と突き合わせ、
その人に必要な画面だけを表示する。

**1本にする理由(記録として残す)**
1. **バージョン管理事故を防ぐ** — 2026-07-27 に「config だけ更新され EXE のリビルドが漏れる」事故が
   実際に発生している。EXE が2本になると、この手間とリスクが倍になる。
2. **役割変更が Excel 1列で済む** — 五十嵐様不在時の代理、購買担当の増員、設計部員の異動が
   再ビルド・再配布なしで対応できる。
3. **分けてもセキュリティ上の意味がない** — 認証なしの社内前提であり、EXE を入手すれば
   どの画面も開ける。2本にしても権限分離にはならず、運用コストだけが増える。

> 「誰が依頼したか」は Windows アカウントによる**自己申告ベース**である(認証基盤がないため)。
> 社内利用では実務上十分だが、厳密な本人証明ではない点を明記しておく。

#### 5.1.1 設計部員モード(往路)

1. 工番を選ぶ(DOVE マスタ検索。**未登録工番も選べる** / 「工番未定」も選べる)
2. 部品リスト Excel を選ぶ
3. 宛先・CC は**マスタExcelから自動設定**(手動追加も可)
4. 件名・本文を自動生成(画面上で編集可)
5. 送信 → 成功後に DOVE へ依頼を登録

- **送信元は操作している本人の Outlook アカウント**。
  既存 `mailer.find_outlook_account(outlook, email)` を流用し、マスタExcelの本人メールで解決する。
- 部品リスト Excel は**メールに添付**する。

#### 5.1.2 購買モード(五十嵐様 / 復路)

1. DOVE から **未対応の依頼一覧**を取得して表示
   - **工番未定の依頼は一覧の先頭に固める**(決定 / 埋もれによる手配漏れを防ぐため)
   - 以降は依頼日の古い順
2. 対象の依頼を選ぶ
3. 手配結果のスキャンPDFを選ぶ
4. **依頼元の設計部員へ返信メール**(CC はマスタExcelから自動設定)
5. DOVE に回答PDFを登録し、ステータスを更新

- 工番未定の依頼に、この画面から**工番を後付けで紐づけられる**。

#### 5.1.3 共通

- 起動時にマスタExcel(ファイルサーバ固定パス)と config.toml を読み込む。
- DOVE 登録は**冪等**。メール送信成功後に登録が失敗した場合、
  **メールを再送せずに登録だけ再試行**できる(出図EXEの `_retry_register_only` と同方式)。
  - 冪等キーは EXE が生成する `client_request_id`(UUID)。同じキーで再送された場合、
    **依頼レコードもアップロードファイルも二重に作らない**。
  - 再試行時にファイルがまだ保存されていなければ、そのとき保存する
    (メール送信済み・ファイル未保存という中途半端な状態を残さない)。
- Windows アカウントがマスタExcel に無い場合は、起動時にダイアログで通知して終了する。

### 5.2 マスタExcel(宛先・CC・役割)

**ファイルサーバ上に1つだけ置き、全員がそこを読む**(EXE と一緒に配布しない)。
出図EXEが工番マスタで採用している方式と同じ。読むだけ(`read_only=True`)、書き込み・削除はしない。

想定する列:

| 列 | 用途 |
|---|---|
| ID | 連番 |
| 名前 | 表示名・署名 |
| Windowsアカウント | 起動時の本人判定キー |
| メールアドレス | 送信元アカウントの解決、宛先 |
| 役割 | `設計` / `購買`(画面の切替) |
| 依頼CC | 設計→購買 の送信時に自動挿入する CC(`○`/`CC`/`×`) |
| 回答CC | 購買→設計 の返信時に自動挿入する CC(`○`/`CC`/`×`) |

- 既存 `members.py` の `flag_kind()`(`○`/`〇`/`O` → TO、`CC` → CC、それ以外 → 対象外)を流用する。
- 列構成は実装前に実物で確定する(§6 T-07)。

### 5.3 DOVE 側の表示方針(重要)

**記録は全部入れる。表示は最小限から始める。**

| 対象 | DOVE UI での既定表示 |
|---|---|
| 工番に紐づいた購入依頼 | **表示する** — 工番詳細に「購入部品依頼」タブを新設(既存「工番別指示書」タブと同形) |
| 工番未定の依頼 | **表示しない**(DB には記録。EXE の購買画面で扱う) |
| 購入依頼だけで発生した工番(`origin = purchase`) | **工番一覧に表示しない**(既定フィルタから除外) |

- 五十嵐様の未対応一覧・ステータス操作は **EXE 側の画面で完結**させる(実務の主戦場であるため)。
  よって DOVE フロントの改修は**当面タブ1つのみ**で成立する。
- 将来必要になれば、フィルタ1つで表示に切り替えられる(DB には入っているため)。

#### 5.3.1 「表示しない」を確実に担保するための実装要件

「表示しない」は放置すると漏れる。以下を実装要件として明記し、**テストで固定する**:

- 工番一覧の**件数カウント**(`GET /jobs/counts`)に `origin = purchase` の工番が混ざらないこと
- 工番一覧(`GET /jobs`)の既定レスポンスに含まれないこと
- 工番の**検索結果**に紛れ込まないこと
- 上記が**リグレッションテストとして残っている**こと

### 5.4 Excel 形式の記録

- **Excel は出力物であって、データベースではない。**
- DOVE から現在のステータス一覧を **Excel で書き出す**機能を用意する。
- 集計・報告・紙での確認はこの出力を使う。Excel を編集しても DOVE には戻らない(一方向)。

## 8. ファイルの取り扱い(CLAUDE.md §2.1 / §2.2 準拠)

**部品リスト Excel は各自のPC上に置かれる運用が確定した(D-13)。** ローカルパスは
他者にも DOVE にも解決できないため、**往路・復路とも「アップロード方式」**とする。

| 対象 | 方式 | 保存先 |
|---|---|---|
| 部品リスト Excel(往路) | **アップロード** | `/mnt/uploads/purchase/{request_id}/` |
| 手配結果スキャンPDF(復路) | **アップロード** | `/mnt/uploads/purchase/{request_id}/replies/` |

- メールへの添付は、**依頼者PC上のローカルファイルをそのまま Outlook に添付**する
  (アップロードとは独立。EXE 側の処理は変わらない)。
- 実装は既存の `attachments.py` の `_save_uploaded_file()` を流用する:
  - `open(path, "xb")` による**排他作成**。既存ファイルがあれば `FileExistsError` → **上書きしない**
  - **50MB 上限**(Content-Length の事前チェック + 実バイト数での再検証)
  - ファイル名サニタイズ(Path Traversal 対策)、`resolve_under()` で `/mnt/uploads` 配下を強制
- 保存先を `{request_id}` 単位のディレクトリに分けることで、
  **`部品リスト.xlsx` のような汎用名が多数来ても衝突しない**。元ファイル名は表示用に DB へ保持する。
- **コピー元(依頼者PC上のファイル)には一切触らない。** 読み取ってアップロードするのみで、
  移動・削除・改名はしない。
- 拡張子・中身の検証を行う(Excel: `.xlsx`/`.xlsm`、回答: PDF の magic bytes)。

### 8.1 アップロード方式にしたことによる副次的な利点

- **リンク切れが原理的に起きない。** パス参照ではないため、依頼者が後からファイルを移動・削除・
  改名しても、DOVE 側の記録は失われない(既存機能で発生しているリンク切れ問題の回避)。
- **バックアップ対象になる。** 各自のPC上のファイルは社内バックアップの対象外だが、
  `/mnt/uploads` 配下に入ることで保全される。

## 9. 非機能・制約

- 認証なし・社内LAN限定(DOVE と同方針)。EXE は `http://dove/api/v1/...` を呼ぶ。
- EXE は都度起動(常駐しない)。技術は **Python + Tkinter + PyInstaller**(既存資産の流用のため)。
- 削除・上書き・rename 禁止。連携は原則パス参照。
- 秘匿情報(メール本文・PII)を `action_logs` の payload に入れない(出図連携と同じ規約)。
- 配布物: `購入部品追加依頼.exe`(名称は要確認) + `config.toml`。マスタExcel は同梱しない
  (ファイルサーバの固定パスを参照)。

## 11. 受け入れ基準(ドラフト)

1. 設計部員が EXE から部品リスト Excel を選び、ボタン一つで五十嵐様へ**本人のアカウントから**送信できる。
2. 送信成功後、DOVE に依頼が記録され、**DOVE に未登録の工番でも**自動作成されて紐づく。
3. 工番未定の依頼が登録でき、五十嵐様の一覧で**先頭に表示**される。
4. 五十嵐様が未対応一覧から依頼を選び、スキャンPDFを添付して**依頼元の設計部員へ返信**でき、
   ステータスが完了になる。
5. 依頼元の設計部員が、自分の依頼のステータスを確認できる。
6. DOVE の工番詳細で、その工番の購入依頼履歴を参照できる。
7. **DOVE の工番一覧の見た目と件数が、本機能の導入前後で変わらない**(購入依頼のみの工番・
   工番未定の依頼が混ざらない)。これがテストで固定されている。
8. メール送信は成功したが DOVE 登録が失敗した場合、**メールを再送せずに**登録だけ補完できる。
   再試行しても依頼レコード・アップロードファイルが二重にならない。
9. 依頼者PC上の部品リスト Excel が DOVE にアップロードされ、**五十嵐様が開ける**。
   同名ファイル(`部品リスト.xlsx` 等)が複数の依頼から来ても取り違えない。
10. 依頼者PC上の元ファイルに対して、移動 / 削除 / 改名 / 上書きが発生しない。
11. ファイルサーバ上の既存ファイルのコピー / 削除 / 上書き / rename が発生しない。

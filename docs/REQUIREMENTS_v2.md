## 0. このアプリの存在意義 (絶対原則)

> 余分なものは不要。目的に沿わないもの・格好つけのシステムは作らない。

### 2 つの柱
1. **2 拠点を繋ぐ連結ツール** (出図 / メール自動化 / 業務フロー)
2. **製造部が現場で使う DX ツール** (図面閲覧 / DXF 寸法 / PDF 編集)

### 必須条件 (これが満たせないなら作る意味がない)
1. **連結がスムーズで確実** — 出図情報・パスリンク・メールが両拠点に確実に届く
2. **製造部が見やすく、寸法計測・PDF編集が確実に使える** — 紙の図面より速くて確実

判断基準: **「この機能はどちらの柱を支えるか?」** 答えられなければ作らない / 消す。

## 1. プロジェクトの 2 つの柱 (詳細)

### 柱 ①「拠点間の業務効率化」(デスクワーク主役)

2拠点体制になり、図面を物理で運ぶ運用が破綻した。これをアプリで置き換える。

| サブ目的 | 概要 |
|---|---|
| (a) 出図管理 & パス共有 | Windows サーバー上の図面ファイルパスをメールで両拠点へ即共有 |
| (b) PDF活用の高度化 | 必要ページだけ抜いて印刷 → 外注へ流す / 差替もアプリで完結 (Marin-PDF を移植) |
| (c) 通信の自動化 | 出図・差替・部品追加のメール文面を自動で組み立て、設計・購買・生産管理を繋ぐ |

### 柱 ②「製造現場のタブレット DX」

| サブ目的 | 概要 |
|---|---|
| (a) 寸法確認の完結 | DXF Viewer + 距離計測で、現場が自分で寸法を拾える (設計への問合せ削減) |
| (b) 物理移動の削減 | 図面を取りに走る必要をなくす。閲覧・パス共有・加工指示をアプリで完結 |

統合点: **1つのアプリで「設計 → 製造現場」まで一気通貫で管理する**。

## 3. メールフロー (重要)

ローカル **Outlook 経由** で送信。送信記録のため自分のローカルアドレスにも CC を入れる。
4 種類のメールテンプレートを「**宛先デフォルトつき**」でDBに保存し、送信時に **都度宛先を編集可能** にする。

### 3.1 4種類のメールテンプレート

| # | 種別 | 送信者 (デフォルト) | 宛先 (デフォルト) | 添付 / 本文挿入 |
|---|---|---|---|---|
| T1 | **設計出図メール** (= 設計修正完了の出図通知) | 木場さん (固定) | 関係部署全員 (具体メンバーは管理画面で編集可能) | **パスリンクのみ** (図面はサーバ所定フォルダ) |
| T2 | **差し替え図面メール** | 設計者 (都度可変) | 田中さん (生産管理) | **パスリンク + 差し替え PDF** の両方 |
| T3 | **追加購入部品 手配依頼** | 設計者 (都度可変) | 五十嵐さん (資材購買) | **PDF (Excel→PDF) を基本** + CSV / パスリンクも任意で追加可 |
| T4 | **追加手配完了 通知** (五十嵐さんからの「済」スキャン受領を担当者へ転送) | テンプレ送信者 | 担当者 (元の依頼者) | **PDF スキャン画像のみ** |

### 3.2 ワークフロー

```
[設計出図] (#2 工程完了)
   │
   └─→ T1 メール (木場さん → 関係部署全員)
        │  パスリンクを添える / 図面はサーバ所定フォルダに保存済
        │
        ├─→ 五十嵐さん (#4 購入部品手配 開始)
        ├─→ 箱崎さん (#3 在庫チェック / #5 材料取り 開始)
        └─→ その他関係部署

[差し替え発生時]
   └─→ T2 メール (設計者 → 田中さん)

[追加部品発生時]
   └─→ T3 メール (設計者 → 五十嵐さん)
        │
        └─← 五十嵐さんから「済」スキャン返信
             │
             └─→ T4 メール (担当者へ済通知を転送)
```

### 3.3 テンプレート保存仕様 (DB)

各テンプレートに以下を **永続保存** する。**管理画面 (admin) からテンプレート本体と宛先デフォルトを編集可能**。

| カラム | 型 | 内容 |
|---|---|---|
| code | str | T1 / T2 / T3 / T4 など一意コード |
| name | str | 「設計出図メール」等 |
| default_from | FK→users | 送信者デフォルト (例: T1 は木場さん固定) — null なら都度入力 |
| default_to | list[FK→contacts] | 宛先デフォルト (連絡先マスタからの選択) |
| default_cc | list[FK→contacts] | CC デフォルト (送信記録用に自分のアドレスを含めるのが基本) |
| subject_template | str | 件名テンプレ (プレースホルダ可: `{{工番}}` 等) |
| body_template | str | 本文テンプレ |
| attachments_mode | enum | path_link / pdf_attach / both |

### 3.4 管理画面 (admin) で編集できる対象

ユーザーが「裏側から」設定したいのは、以下 4 種類のテンプレートの **「誰が、誰に送るか」**:

| 項目 | 対象テンプレ | 送信者デフォルト | 宛先デフォルト |
|---|---|---|---|
| 1. 設計出図 | T1 | 木場さん (固定可) | 関係部署全員 (= 管理画面で編集) |
| 2. 差し替え | T2 | 設計者 (都度) | 田中さん (デフォルト・編集可) |
| 3. 購入部品 追加手配 | T3 | 設計者 (都度) | 五十嵐さん (デフォルト・編集可) |
| 4. 追加手配 完了通知 | T4 | テンプレ送信者 (都度) | 担当者 (元の依頼者・編集可) |

### 3.5 送信時 UI

- テンプレ選択 → デフォルト宛先がロード
- 送信者・宛先・CC は **都度編集可能** (連絡先マスタからチェック追加 or 自由入力)
- 編集結果は当該送信ログには残るが、テンプレ本体のデフォルトは変えない (今回だけ変更)
- テンプレ本体・デフォルト宛先の編集は管理画面 (admin) で別途

### 3.4 実装観点

- 既に `outlook-agent/` (Windows ローカル常駐 exe + COM 直送) を準備済み → これを使う
- 「Outlook 経由 + 自分にも送る」要件は agent ↔ FastAPI 連携で満たす
- EML 生成 (fallback) も並行で残す (Outlook が起動していない時用)

## 3.6 ファイルパスの登録方法 (出図・関連資料・部品リスト 共通)

アプリにファイル本体をアップロードするのは原則しない (= Windows サーバ上のファイルを **パス参照** で扱う)。
PDF差替 (アップロード) のみ例外。

採用方式は **A + B の併用**。

### A. パス貼り付け
- ユーザーは Explorer でファイルを右クリック → **「パスのコピー」** (Windows 標準)
- アプリの入力欄に Ctrl+V
- 受け取った文字列は UNC (`\\server\share\...`) と Windows ドライブ (`Z:\...`) の両方をサーバ側で正規化
- サーバ側で「許可ルート (`/mnt/fileserver` 配下) を外れていないか」を必ず検証 (Path Traversal 防止)

### B. アプリ内フォルダブラウザ (Explorer 風 UI)
- 既存の `/v1/files/browse?path=...` を使ったモーダル内 UI
- 見た目: フォルダ/ファイルアイコン + 「上へ↑」ボタン + パンくず — Windows Explorer と同じ操作感
- ダブルクリックでフォルダ降下、ファイル選択で確定
- **初期表示**:
  - 既定: 最上位 (`/mnt/fileserver/`)
  - 工番が選択済の文脈 (例: 出図モーダル) では、`Drawings/{工番}/` まで自動で降りる試行 (無ければ最上位にフォールバック)
- 確定すると相対パスが入力欄に自動セット

### 採用しない
- **C. パス自動生成**: 命名規約強制が運用に合わないため見送り
- **D. ドラッグ&ドロップでパス取得**: ブラウザ仕様で絶対パスが取れず、ローカル常駐 exe が必要となり複雑

### 適用場所
| 画面 | A | B |
|---|---|---|
| 出図モーダル (PDF パス入力) | ✅ | ✅ |
| 関連資料追加 | ✅ | ✅ |
| 部品リスト バージョン追加 | ✅ | ✅ |
| T1 出図メール本文 内のパスリンク (自動挿入) | パスは上記で確定したものを使う | - |

## 6.1 関連書類タブ群の再設計 (重要)

詳細画面の **「関連資料 / 差し替え図面 / 部品リスト / メール」** ボタンは、現状は **入力モーダル** が開く実装だが、これは誤り。本来の意図:

> **「タブごとが、対応する書類を入れておくフォルダのような役割」**
> → クリックすると **その軸に紐づく書類の中身を確認する画面** が開く

書類の新規登録はそのフォルダ画面の中のサブ操作として行う (画面の主役ではない)。

### タブ別 仕様

#### (1) 関連資料
- 軸に紐づく関連資料 PDF を **一覧で表示**
- PDF が入っていれば **その場でプレビュー** (Marin-PDF 統合後はインラインビューア)
- 各エントリ: ファイル名 / パス / 登録日時 / メモ
- 行クリックで該当 PDF をメイン領域に表示 or 新規タブで開く
- 「+ 追加」はフォルダ画面下部の小ボタン

#### (2) 差し替え図面
- 軸に紐づく差替履歴を **時系列で表示**
- 各エントリ: 更新日時 / 担当者 / 元バージョン v? / 差替後 PDF パス / メモ
- (a) **履歴の表示** (いつ / 誰が)
- (b) **パスリンク・紐付け表示** (元のバージョン → 差替後ファイル)
- (c) **リンク押下で該当ファイルが開く**
- 「+ 差替を登録」はフォルダ画面下部の小ボタン

#### (3) 部品リスト
- 軸に紐づく部品リスト全バージョンを **履歴で表示**
- 行クリックで該当版を選択・閲覧
- 最新版に「LATEST」バッジ
- 「+ 新バージョン追加」はフォルダ画面下部の小ボタン

#### (4) メール履歴 (閲覧専用)
- 当該工番/軸に紐づくメール送信ログを **時系列で閲覧** するだけのタブ
- 各エントリ: 送信日時 / 種別 (T1/T2/T3/T4) / 件名 / 宛先 / 送信者 / EML ダウンロード
- **このタブから「メール作成」はしない** (= スタンドアロンのメール作成は廃止)
- 「メール作成」は各業務アクションのフロー内で起こす (下記 6.2 参照)

## 6.2 メール作成は業務アクションに統合する (重要)

現状の **「メール作成」を独立ボタンにする実装は誤り**。メール送信は常に何らかの業務アクションのアウトプットなので、それぞれのフロー内で起こす。

| 業務アクション (起点画面) | 直結するメールテンプレ | 振る舞い |
|---|---|---|
| **出図** (出図モーダル → バージョン登録) | **T1 設計出図** | バージョン登録後に「+ T1 メール送信ダイアログ」が同フローで開く。本文はテンプレ+工番/軸/パス自動挿入。送信者デフォルト=木場さん |
| **差し替え図面 登録** (差替タブ「+ 追加」) | **T2 差し替え** | 差替 PDF 登録後に T2 メール送信ダイアログ。宛先デフォルト=田中さん |
| **追加部品 発注** (部品リストタブ「+ 追加発注」) | **T3 追加部品** | 部品リストバージョン追加後に T3 メール。宛先デフォルト=五十嵐さん |
| **追加部品 済受領** (T3 の返信を取り込む) | **T4 済通知** | 「済」スキャン PDF を取り込むと、自動で T4 メール作成ダイアログが開く。担当者宛て |

### 共通の挙動
- ダイアログには **テンプレートが事前選択された状態** で開く (種別選び直しは可)
- 宛先・件名・本文はデフォルトロード → **都度編集可** (テンプレ本体は変えない)
- 「送信せず下書き保存」「Outlook で開く (EML)」「Outlook agent で送信」を選べる
- 送信したらメール履歴タブに自動で追記される

### 廃止する UI
- 詳細画面アクション行の「メール」単独ボタン → **削除**
- スタンドアロンの MailModal → **削除** (代わりにアクション後のフロー組込)

## 6.3 グローバルなメール履歴

工番別の履歴 (6.1 (4)) に加えて、管理画面に **横断的なメール送信ログ** ページを置く:
- 全工番にわたる送信履歴を新着順で表示
- フィルタ: テンプレ種別 / 送信者 / 期間 / 工番
- 失敗ログ (status=failed) を上に固定して可視化

### 共通仕様: インライン「リンク切れ」表示 (方式 (c) 採用)

各タブの一覧で、参照先ファイルが SMB サーバ上に存在しない場合、**その行に「リンク切れ」バッジ** を表示する。

**判定の流れ**:
1. **既存スケジューラ** が 1時間ごとに `link_check_results` を更新 → 普段はこの結果を一覧 API でJOINして返す
2. 各タブ画面に **「再チェック」ボタン** を置く → 押されると、当該軸の参照先ファイルだけ即時 `is_file()` 確認して結果更新
3. リアルタイム性は再チェックボタンで担保、コストは普段のスケジューラ判定で抑える

**UI**: 行末に赤バッジ `🔗❌ リンク切れ` + tooltip でパス表示。出図 PDF (`versions.pdf_path`) / DXF / 関連資料 / 差替 / 部品リスト 全てに適用。

## 6.4 編集後の新バージョン保存 (Marin-PDF 連携の核心)

**Marin-PDF と PM の本質的な違い**: PM は **path 参照ベース** (元 PDF はサーバ上にある)。編集結果は **新バージョンとして元と同じフォルダに保存** する (= 旧版は無傷で残る)。

### フロー
```
[元] Drawings/25214/昇降軸/rev_01.pdf     (read 専用、無傷)
       │ fetch bytes
       ▼
[編集] ブラウザ in-memory (Marin-PDF コア)
       │ ページ差替 / 必要ページ抽出 など
       │ 完成バイトを生成
       ▼
[保存] Drawings/25214/昇降軸/rev_02.pdf   (新規作成・既存衝突は 409 で失敗)
       │
       ▼
[DB] versions テーブルに新行 (version_no = 2, pdf_path = "Drawings/.../rev_02.pdf")
       │
       ▼
[UI] 詳細画面の「最新版」表示が rev_02 に切替
```

### 命名規約の自動採番
バックエンドが既存ファイル名から命名パターンを推定:
- `rev_01.pdf` → `rev_02.pdf`
- `v_001.pdf` → `v_002.pdf`
- `Rev.A.pdf` → `Rev.B.pdf` (アルファベット採番)
- 推定不能なら `{stem}_v{N+1}.{ext}` の自動形式 (例: `drawing_v2.pdf`)

ユーザが UI で名前を手動指定することも可能 (デフォルト推定値を pre-fill)。

### 印刷 (必要ページ抽出)
書込なし、ブラウザ in-memory で完結 → window.print()。元 PDF は無傷、サーバ書込なし。

### CLAUDE.md §2.2 改訂と整合
- SMB マウントは `:rw` に変更
- アプリ層で「新規作成のみ・上書き禁止・削除禁止」を強制
- 本番では Windows ACL でも二重防御 (Modify/Delete/Rename 権限剥奪)

### pdf_replacements テーブルの扱い
旧設計では PDF差替を `/mnt/uploads/replacements/` に別保存していたが、本方針では **不要**。差替も「単に新バージョンを保存する」操作に統合される。

`pdf_replacements` テーブルは **互換のため残置** (CLAUDE.md §2.1 で DROP 禁止)。新規 UI では使わない。将来必要なら「ページ単位の差替メタ情報」用に再活用可能。

## 7. v1 (MVP) スコープ - 確定 (Round 4)

**A〜G 全フェーズを v1 に含める。** 柱①②両方を完成させてリリースする。

### 実装順序 (推奨)
```
A (刈り込み)
  └→ E (パス取得UI)            ← 各登録モーダルの基礎
      └→ B (4タブ フォルダ的view)
          ├→ D (リンク切れインライン)  ← B のリストに被せる
          └→ C (メール業務統合)        ← B の追加サブボタンから起こす
              └→ F (Marin-PDF 移植)    ← PDFビューア完全置換
                  └→ G (タブレット最適化)
```

A は他フェーズと並行で随時、E はモーダル系の前提なので先行、最後の G は F の品質が整ってから取り組む。
